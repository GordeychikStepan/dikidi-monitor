# 🚗 Мониторинг свободной записи к автоинструктору DIKIDI

Готовый проект для **iPhone + GitHub + Telegram + Supabase**. Сайт размещается на GitHub Pages, а проверка расписания выполняется в GitHub Actions. Логин, настройки, последние 100 проверок, изменения слотов и очередь уведомлений хранятся в Supabase.

**Рабочая цель:** инструктор **4145159**, услуга **22479921**, автошкола **1926065**. Инструктор **4145151** используется только при включённом тестовом режиме. Настройка `target_master_id` изначально равна `4145159`. Переключить её можно в настройках сайта; редактировать код для теста не нужно.

> **Проверено 23.09.2026:** публичный запрос, который выполняет страница DIKIDI, показал у тестового инструктора окна 24.09 в 09:00 и 10:30, а также 25.09 в 16:30. У основного инструктора ответил пустым списком. Эти данные могут измениться в любой момент. **Запуск с IP GitHub Actions до настройки вашего репозитория проверить невозможно**: если DIKIDI откажет его серверу, система покажет ошибку и сообщит о ней в Telegram, а не объявит, что записей нет.

## Что внутри

| Часть | Где работает | Что делает |
| --- | --- | --- |
| `index.html`, `css/`, `js/` | GitHub Pages, Safari на iPhone | Адаптивный кабинет, тёмная/светлая тема, настройка, история, вход |
| `src/dikidi.mjs` | GitHub Actions | Читает запрос расписания DIKIDI и все доступные даты |
| `src/worker.mjs` | GitHub Actions | Планирует проверки, записывает результат, отправляет очередь Telegram |
| `db/schema.sql` | Supabase | Таблицы, права доступа, сравнение слотов и защита от параллельной обработки |
| `.github/workflows/check.yml` | GitHub Actions | Запуск раз в 5 минут и ручной запуск |
| `tests/` | GitHub Actions | Проверка сравнения слотов, ответа DIKIDI, Bot API и заголовков Supabase |

На сайте кнопка **«Проверить сейчас»** открывает страницу GitHub Actions. Там нужно дополнительно нажать **Run workflow**. GitHub Pages не умеет сам безопасно запускать workflow без серверной части или токена доступа, поэтому кнопка честно сообщает о дополнительном шаге. **Токен GitHub никогда не вставляйте в `js/config.js`.**

## Шаг 0. Сохранить проект на iPhone

1. Скачайте приложенный архив проекта в приложении ChatGPT. Если Safari спросит, куда сохранить, выберите **Файлы → На iPhone → Загрузки** или iCloud Drive.
2. Откройте приложение **Файлы**, найдите `.zip`, нажмите на него один раз: iPhone создаст папку `dikidi-monitor`.
3. Откройте папку. В ней должны лежать `index.html`, `README.md`, `package.json`, `css`, `js`, `src`, `db`, `tests` и скрытая папка `.github`. **Сам ZIP на GitHub загружать бесполезно: GitHub не распакует его как проект.**
4. В Safari при необходимости нажмите **аА → Запросить настольный веб-сайт**. GitHub и Supabase имеют плотный интерфейс; горизонтальная ориентация iPhone иногда удобнее.

## Шаг 1. Создать Telegram-бота

1. Откройте Telegram, найдите **[@BotFather](https://t.me/BotFather)** и убедитесь, что это официальный бот с подтверждённым именем.
2. Нажмите **Start** и отправьте `/newbot`.
3. Введите любое название, например `Запись к инструктору`.
4. Введите свободное имя, оканчивающееся на `bot`, например `StepanDrivingSlotsBot`.
5. BotFather пришлёт **Bot Token**, похожий на `123456789:AA...`. Скопируйте его временно в защищённое место. **Не отправляйте его в чат с другими людьми и не добавляйте в файлы проекта.**
6. Откройте своего нового бота и отправьте ему `/start`. Бот не может первым написать вам в личный чат, пока вы не открыли с ним диалог.

### Как узнать Telegram Chat ID без сторонних ботов

1. В Safari откройте адрес, подставив ваш настоящий токен **только на своём телефоне**: `https://api.telegram.org/botВАШ_ТОКЕН/getUpdates`.
2. Найдите в ответе `"message"`, затем внутри него `"chat":{"id":...}`. Число в `chat.id` — это ваш **TELEGRAM_CHAT_ID**. Например, у `"id":123456789` ID равен `123456789`.
3. Если ответ `"result":[]`, отправьте своему боту ещё одно сообщение `/start` или `тест`, затем обновите Safari. Если на боте уже настроен webhook, `getUpdates` может не работать; для нового бота webhook обычно отсутствует.
4. Закройте вкладку с токеном после копирования ID. Ссылку с токеном не публикуйте и не пересылайте. При подозрении на утечку перевыпустите токен через BotFather.

### Загрузка файлов через github.com на iPhone

1. На странице репозитория нажмите **Add file → Upload files → choose your files**.
2. Выберите файлы **из корня** папки проекта: `index.html`, `README.md`, `package.json`. Внизу страницы нажмите **Commit changes**. Если был создан стандартный README, подтвердите его замену.
3. Для папок, если Safari позволит перетащить всю папку из приложения «Файлы», перетащите `css`, `js`, `src`, `db` и `tests` в окно загрузки; после коммита **обязательно проверьте полные пути** на GitHub. На iPhone перетаскивание папок поддерживается не во всех версиях интерфейса.
4. **Гарантированный способ, если перетаскивание не сработало:** создайте первый файл нужной папки через **Add file → Create new file**. В поле имени наберите путь со слешем, например `css/style.css`, затем вставьте содержимое одноимённого файла из архива и нажмите **Commit changes**. GitHub создаст папку автоматически. Так же создайте `js/config.js`, `src/core.mjs`, `db/schema.sql`, `tests/core.test.mjs`.
5. Когда папка уже существует, откройте её на GitHub → **Add file → Upload files** и выберите остальные файлы этой папки из «Файлов» iPhone. Проверьте, что `src/worker.mjs` оказался именно в `src/`, а `js/app.js` — именно в `js/`.

Вставьте его содержимое из архива (или из документа `ALL_FILES.md` рядом с архивом), нажмите **Commit changes**. Это особенно удобно, поскольку iPhone может скрывать папки с точкой в приложении «Файлы».
8. Сверьте список файлов с деревом выше. Нельзя оставлять `check.yml` только в корне или загрузить сам ZIP вместо файлов.

Если удобнее редактировать код в браузере, откройте `https://github.dev/ВАШ_ЛОГИН/dikidi-monitor`; там можно править файлы и выполнить **Source Control → Commit & Push**. Это редактор в браузере, ПК не нужен. Для простого изменения `js/config.js` обычный редактор GitHub удобнее.

## Шаг 3. Supabase: база данных и один владелец

1. В Safari откройте [supabase.com/dashboard](https://supabase.com/dashboard), создайте аккаунт и войдите. Выберите бесплатный план **Free**.
2. Нажмите **New project**, выберите организацию, название например `dikidi-monitor` и задайте **пароль базы данных**. Пароль базы нужен только для создания проекта; **не вставляйте его в сайт**. Выберите близкий регион и дождитесь создания проекта.
3. В меню проекта откройте **Authentication → Users → Add user**. Если есть **Create new user**, введите вашу электронную почту и отдельный сильный пароль, включите подтверждение пользователя, если есть такая опция. Если показано только **Send invitation**, отправьте приглашение самому себе, откройте письмо и задайте пароль. Должен существовать **ровно один подтверждённый пользователь**. Его email и пароль понадобятся для входа на сайт.
4. Для безопасности откройте **Authentication → Sign In / Providers** (в некоторых версиях **Authentication → Settings**) и выключите **Allow new users to sign up** после создания своего пользователя. Существующий пользователь сможет входить.
5. На GitHub откройте загруженный файл `db/schema.sql`, нажмите **Raw** и скопируйте весь текст. Либо откройте этот файл из папки проекта в «Файлах» и скопируйте текст. В Supabase откройте **SQL Editor → New query**, вставьте весь текст и нажмите **Run**. В конце должен появиться результат с **одной строкой**, где `target_master_id=4145159`, `interval_minutes=10`, `notification_mode=new`. Если пользователей 0 или больше 1, SQL специально остановится с понятной ошибкой — используйте отдельный новый проект с одним владельцем.
6. Откройте **Project Settings → API Keys** (иногда раздел **Connect / API**). Скопируйте:

| Значение Supabase | Куда вставить | Можно ли публиковать? |
| --- | --- | --- |
| Project URL `https://...supabase.co` | `SUPABASE_URL` в GitHub Secrets **и** `SUPABASE_URL` в `js/config.js` | Да, URL сам по себе не секрет |
| Publishable key `sb_publishable_...` | Только `SUPABASE_PUBLISHABLE_KEY` в `js/config.js` | Да, **только при включённых RLS**, как в нашем SQL |
| Secret key `sb_secret_...` | Только `SUPABASE_SECRET_KEY` в GitHub Actions Secrets | **НЕТ**. Обходит RLS, не вставляйте в `js/config.js` |

7. На GitHub откройте **`js/config.js` → карандаш Edit**. Замените ровно три строки: ваш `SUPABASE_URL`, ваш `SUPABASE_PUBLISHABLE_KEY`, `GITHUB_REPO='ВАШ_ЛОГИН/dikidi-monitor'`. Нажмите **Commit changes**. Пример **без настоящих ключей**:

```js
export const SUPABASE_URL = 'https://exampleproject.supabase.co';
export const SUPABASE_PUBLISHABLE_KEY = 'sb_publishable_...';
export const GITHUB_REPO = 'Stepan/dikidi-monitor';
```

8. **Никогда** не вставляйте `sb_secret_...`, Telegram Bot Token, пароль базы или пароль от сайта в `index.html`, `js/`, README либо публичный репозиторий.

## Шаг 4. Добавить четыре GitHub Secrets

Откройте репозиторий в Safari → **Settings → Secrets and variables → Actions → New repository secret**. Если на узком экране не видно `Settings`, прокрутите горизонтальную панель вкладок или включите настольный вид Safari. Создайте четыре секрета по одному:

| Имя секрета — набирайте точно | Значение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Токен из BotFather |
| `TELEGRAM_CHAT_ID` | Число `chat.id` из `getUpdates` |
| `SUPABASE_URL` | URL проекта Supabase |
| `SUPABASE_SECRET_KEY` | **Secret key `sb_secret_...`**, не publishable |

Нажимайте **Add secret** после каждого. GitHub больше не покажет сохранённое значение: если ошиблись, откройте имя и замените значение. **Не создавайте публичные GitHub Variables вместо Secrets для токенов.**

## Шаг 5. Включить GitHub Actions и проверить Telegram

1. Откройте вкладку **Actions** репозитория. Если появится приглашение включить workflow для репозитория, подтвердите **Enable / I understand my workflows, go ahead and enable them**.
2. В списке workflow нажмите **DIKIDI monitor**. Если его нет, проверьте путь `.github/workflows/check.yml` и ветку по умолчанию `main`.
3. Нажмите **Run workflow**. В выборе действия укажите **`telegram_test`**, оставьте ветку **main** и нажмите **Run workflow** ещё раз.
4. Появится новый запуск. Откройте его → **monitor → Check DIKIDI or Telegram**. При успехе увидите `Test Telegram notification sent` и получите тестовое сообщение в личном чате. Тест **не** проверяет DIKIDI и не подменяет состояние расписания.
5. Если Telegram написал `chat not found`, проверьте Chat ID, отправьте `/start` своему боту. При `401 Unauthorized` проверьте Bot Token. При ошибке Supabase проверьте URL, `sb_secret_...` и выполненный SQL.

## Шаг 6. Запустить первую проверку

1. В том же workflow нажмите **Run workflow**, выберите **`check`** и нажмите **Run workflow**.
2. Откройте запуск → **monitor → Check DIKIDI or Telegram**. Ожидаемые строки: `Starting DIKIDI check`, `Target: основной (4145159)`, `Found N dates`, `Found N available slots`, `New slots: N`, `Check completed: empty/available`.
3. Если DIKIDI ответил 403, 404, 429, 500 или таймаутом, запуск будет красным; в Supabase сохранится статус **error**, а при включённых уведомлениях об ошибках придёт Telegram. **Ошибка никогда не означает «мест нет».**
4. Плановые проверки будут выполняться через workflow по расписанию. В настройках сайта можно отключить мониторинг или изменить период. Ручной запуск `check` выполняется даже при выключенных плановых проверках.

## Шаг 8. Проверка на другом инструкторе и возврат к основному

1. На сайте войдите, откройте **Настройки → Кого проверять → Тестовый · 4145151**. Подтвердите предупреждение и нажмите **Сохранить настройки**.
2. Откройте **Система → Перейти к Actions → Run workflow → `check` → Run workflow**.
3. В логах должна быть строка `Target: тестовый (4145151)`. Вернитесь на сайт и нажмите **Обновить**. Если у него ещё открыты окна, они появятся в панели. Откройте DIKIDI по кнопке и сравните время. Наличие окон на 23.09.2026 было подтверждено, **на момент вашего теста они могут уже исчезнуть**.
4. Если появится Telegram, в нём обязательно будет `Инструктор: тестовый (4145151)`, а ссылка будет содержать `m=4145151`. Эти окна **не выдаются за записи основного инструктора**.
5. **Сразу после теста** откройте **Настройки → Основной · 4145159 → Сохранить настройки**. При желании ещё раз вручную запустите `check`. Проверьте в логах `Target: основной (4145159)`.

Для каждого из двух инструкторов хранится **свой** снимок слотов. Если у основного слот появился → исчез → появился снова, повторное появление считается новым событием. Переключение на тестового не уничтожает снимок основного.

## Как работают уведомления

На странице **Настройки** выберите один основной режим:

- **Только новые окна:** сообщение только для слотов, которых не было в предыдущей **успешной** проверке этого же инструктора. На самой первой успешной проверке уже открытые окна считаются новыми.
- **После каждой проверки:** сообщение после каждого успешного фактического запроса, даже при 0 окон. Пропущенные запуски, когда выбранный интервал ещё не наступил, сообщений не создают.
- **Когда окон нет:** сообщение только после успешной проверки с пустым списком.

Отдельные переключатели: **ошибки** (по умолчанию включены) и **исчезновение записей** (по умолчанию выключено). Ошибка не изменяет предыдущий снимок; после восстановления мониторинг сравнивает результат с последним успешным. Отправка идёт через очередь в Supabase: если Telegram временно недоступен, сообщение останется неотправленным и повторится при следующем запуске. В крайне редком случае успешной отправки и одновременного сбоя записи подтверждения в базу возможно одно повторное сообщение — внешние системы не дают транзакции «отправить Telegram и сохранить в БД».

## Интервалы, ограничения и реальная скорость

GitHub запускает workflow по cron **каждые 5 минут** в моменты примерно `:02`, `:07`, `:12` и т. д. (UTC). Выбор 10/15/30/60 минут в настройках проверяется в базе: промежуточные запуски пропускают запрос к DIKIDI. Время «следующая проверка» — **самое раннее плановое**, а не обещанное точное время.

| Период в настройках | При нормальной работе окно обнаружится приблизительно через |
| --- | --- |
| 5 минут | до 5–10 минут + длительность запроса |
| 10 минут | до 10–15 минут + длительность запроса |
| 15 минут | до 15–20 минут + длительность запроса |
| 30 минут | до 30–35 минут + длительность запроса |
| 60 минут | до 60–65 минут + длительность запроса |

Это **приблизительные**, а не гарантированные сроки. GitHub может задержать или даже пропустить запланированный запуск при высокой нагрузке. В публичном репозитории GitHub **автоматически отключает расписание после 60 дней без активности в репозитории**. Проверяйте вкладку Actions и делайте осмысленное обновление проекта хотя бы раз в месяц; один только открытый сайт или посещение Supabase не является активностью репозитория. Если расписание отключилось, включите workflow снова через Actions. Если свободное окно появилось и исчезло между проверками, система его не увидит.

При большом числе доступных дат код проверяет максимум **31 дату** за один запуск и делает паузу 350 мс между датами. Если дат больше 31, результат считается **ошибкой** и прошлое состояние не затирается. Сетевые ошибки и HTTP 429/5xx повторяются максимум два раза с паузами; HTTP 403/404 не обходятся и сразу считаются ошибкой. CAPTCHA, аккаунты и методы обхода ограничений не используются.

**Нет гарантии, что IP GitHub Actions сможет получать ответы DIKIDI в будущем.** В случае постоянной блокировки из GitHub Actions потребуется разрешённый DIKIDI канал доступа или другой согласованный источник расписания. Простое включение Playwright не даёт гарантии и не заложено как обход ограничений.

## Безопасность и данные

- **Публичны:** HTML/CSS/JS сайта, URL Supabase, `sb_publishable_...`, код GitHub. Публичный ключ безопасен только потому, что SQL включает Row Level Security и разрешает доступ лишь вошедшему владельцу.
- **Секретны:** `sb_secret_...` (обходит RLS), Telegram Bot Token, пароль пользователя. Первые два хранятся в **GitHub Actions Secrets**, пароль пользователя — только в Supabase Auth. Chat ID тоже хранится в Secrets.
- Браузер отправляет запросы с вашим сеансом Supabase, а не с серверным секретом. История и настройки доступны только владельцу. На iPhone сеанс хранится локально в Safari для повторного входа; не входите на чужом устройстве и выходите кнопкой ↪.
- Не копируйте URL `api.telegram.org/bot...` с настоящим токеном в Issues, скриншоты или чат поддержки. Если секрет случайно закоммичен в публичный репозиторий, **сразу перевыпустите** его; удаление файла из последнего коммита не удаляет его из истории Git.

## Что делать при неполадках

| Признак | Что проверить |
| --- | --- |
| Нет workflow во вкладке Actions | Файл должен лежать именно по пути `.github/workflows/check.yml` на главной ветке |
| На сайте не работает вход | `js/config.js`, подтверждённый пользователь Auth, выполненный SQL, логин и пароль Supabase Auth |
| Сайт открывается без CSS/JS | На GitHub должны существовать `css/style.css` и `js/app.js` в папках; обновите Pages |
| Сайт пишет «настройки не найдены» | В SQL Editor проверьте `select * from public.app_settings;` — должна быть одна строка; SQL запускали после создания пользователя |
| Workflow пишет `Supabase: HTTP 401/403` | Проверьте Secrets `SUPABASE_URL`, `SUPABASE_SECRET_KEY` и что ключ начинается `sb_secret_` |
| DIKIDI пишет 403, 404, 429, 500 или timeout | Это состояние **ошибка**. Сверьте ссылку в обычном браузере, откройте лог Actions. Не трактуйте как 0 окон |
| Telegram пишет `chat not found` | Отправьте `/start` боту, перепроверьте `TELEGRAM_CHAT_ID` |
| Telegram пишет `401 Unauthorized` | Перепроверьте `TELEGRAM_BOT_TOKEN` в GitHub Secrets |
| Telegram показывает старый статус | Посмотрите «Ожидают отправки» и последний запуск Actions; при ошибке сообщения остаются в очереди |
| Запуск «Check skipped: not_due» | До выбранного интервала ещё не дошло; ручной `workflow_dispatch` выполняет проверку принудительно |
| `Check skipped: busy` | Предыдущий запуск ещё имеет действующую блокировку. После аварийного завершения срок блокировки 12 минут |
| Сайт пишет «проверки задерживаются» | GitHub schedule задержался/отключён; проверьте Actions и активность репозитория |

## Для тех, кто хочет проверить код отдельно

На компьютере или в GitHub Codespaces: `npm test` проверяет чистую логику без сети и секретов; `npm run check` запускает рабочую проверку только с четырьмя установленными переменными среды. **ПК для обычного запуска не требуется.** Отдельно в браузере проверено, что запрос DIKIDI возвращает у тестового мастера три слота, а у основного — пустой подтверждённый список на дату разработки. Проверка с IP GitHub и доставка именно на ваш Telegram возможны только после ввода ваших собственных Secrets и ручного запуска workflow.
